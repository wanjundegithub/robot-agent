# 会话历史与软删除设计

**日期：** 2026-04-25

**目标：**
修复当前会话历史设计中的两个缺陷：
1. 新建会话后，上一会话没有稳定进入历史列表，用户感知为“历史丢失”
2. 会话在列表中无法删除

同时补充一条明确规则：
3. 如果用户与机器人没有任何交互，则该会话不保留在历史中

---

## 一、现状与根因

### 1. 新建会话后历史“丢失”

现状并不是后端把旧会话删除了，而是前端对“当前会话”和“历史会话”分别维护了两套来源：

- `frontend/src/App.tsx`
  - 负责创建当前会话、切换当前会话、加载当前消息
- `frontend/src/components/SessionReplayPanel.tsx`
  - 自己重新请求会话列表
  - 自己决定哪些会话显示为历史

当前实现中，新建会话后：

- `App.tsx` 创建新的 session 并切换为当前会话
- 旧的当前会话没有通过统一状态模型沉淀为历史项
- `SessionReplayPanel.tsx` 的历史加载只依赖 `currentUserId`
- 因此新建会话这一动作不会稳定触发历史列表的语义更新

结果是：

- 用户刚刚使用过的会话不一定会立即出现在历史列表
- 页面刷新前后展示结果不一致
- 用户误以为历史会话丢失

### 2. 会话无法删除

现有后端已经暴露 `DELETE /api/sessions/{id}`，但语义并不是真正的“从历史中删除”：

- `java-backend/src/main/java/robot/agent/controller/SessionController.java`
  - 提供 `DELETE /api/sessions/{id}`
- `java-backend/src/main/java/robot/agent/service/SessionService.java`
  - `closeSession()` 只是把状态改成 `CLOSED`
- `getSessionsByUserId()` 仍会返回 `CLOSED` 会话

前端目前也没有删除入口，因此删除链路并未形成闭环。

### 3. 空会话不应进入历史

当前前端历史面板通过拉取每个会话消息，再过滤没有用户消息的会话来隐藏空会话。这种方式有两个问题：

- 历史列表语义建立在前端二次推断上，不稳定
- 刷新后是否显示依赖前端再次拉全量消息，成本高且容易不一致

空会话是否属于历史，应该由后端列表接口直接定义。

---

## 二、设计目标

本次改造后的会话历史系统需要满足以下目标：

1. 新建会话后，已发生过真实交互的旧会话必须稳定保留在历史中
2. 未发生任何用户交互的空会话不得进入历史列表
3. 删除会话采用软删除语义，删除后会话从历史列表消失
4. 页面刷新前后，历史列表结果必须一致
5. 前端会话状态以单一数据源管理，避免主页面和历史面板各自维护会话真相
6. 删除当前会话后，页面必须自动切换到新的可用会话

---

## 三、术语与业务语义

### 1. 当前会话

当前正在聊天主界面中使用的会话。它可以是空会话，也可以已经有消息。

### 2. 历史会话

在历史列表中展示的会话，必须满足以下条件：

- 属于当前用户
- 状态不是 `DELETED`
- 至少发生过一次真实用户交互

### 3. 真实用户交互

定义为：该会话下至少存在一次用户发送消息的记录。实现上等价于：

- 会话下至少存在一条 execution
- 且该 execution 的输入变量中能提取出用户消息文本

### 4. 软删除

删除会话不做物理删除，不级联删除 execution 或消息记录，而是将会话状态改为 `DELETED`。  
`DELETED` 会话不再出现在历史列表中，但保留数据库记录，便于审计和后续恢复扩展。

---

## 四、推荐方案

采用以下组合方案：

1. 后端新增 `DELETED` 状态，明确区分“关闭”和“删除”
2. 后端将 `/api/sessions?userId=...` 收敛为“历史会话列表接口”
3. 历史列表只返回：
   - 非 `DELETED`
   - 有真实用户交互
4. 前端由 `App.tsx` 统一维护会话集合、当前会话、创建、切换、删除
5. `SessionReplayPanel.tsx` 改为展示组件，不再自行决定历史真相

这是本项目当前结构下最稳妥的方案，因为它同时解决了：

- 新建会话后历史不稳定
- 删除语义不闭环
- 空会话刷新后回流到历史

---

## 五、架构与职责划分

### 1. 后端职责

后端负责定义历史列表的最终业务语义。

后端必须回答这两个问题：

1. 哪些会话属于历史
2. 哪些会话已经被删除，不应继续展示

前端不再通过“先拿所有 session，再逐个请求消息，再自己过滤”的方式推断历史。

### 2. 前端职责

前端负责会话操作体验与本地状态同步。

前端必须完成：

1. 当前会话与历史会话的统一管理
2. 新建会话后的即时切换
3. 删除会话后的即时列表移除
4. 删除当前会话后的兜底切换

---

## 六、后端设计

### 1. Session 状态扩展

文件：

- `java-backend/src/main/java/robot/agent/model/SessionStatus.java`

新增状态：

- `DELETED`

状态语义：

- `ACTIVE`：当前可用会话
- `CLOSED`：已关闭但仍可作为历史查看
- `EXPIRED`：已过期
- `DELETED`：已软删除，不在历史列表展示

### 2. 会话列表接口语义调整

文件：

- `java-backend/src/main/java/robot/agent/service/SessionService.java`
- `java-backend/src/main/java/robot/agent/repository/SessionRepository.java`

当前的 `getSessionsByUserId()` 不再理解为“用户全部会话”，而是明确理解为“用户历史会话列表”。

它应返回：

- 当前用户的会话
- 排除 `DELETED`
- 排除没有真实用户交互的空会话
- 结果按 `lastActivityAt desc` 排序

实现策略：

1. 先查询该用户下所有非 `DELETED` 的会话
2. 再基于 execution 记录判断每个会话是否存在真实用户消息
3. 保留符合条件的会话并返回

如果当前 repository 不方便直接写复杂查询，可以先在 service 层聚合过滤；后续再视性能情况下推到 repository。

### 3. 删除接口语义调整

文件：

- `java-backend/src/main/java/robot/agent/controller/SessionController.java`
- `java-backend/src/main/java/robot/agent/service/SessionService.java`

`DELETE /api/sessions/{id}` 语义改为：

- 将会话状态改为 `DELETED`
- 更新 `lastActivityAt`
- 不物理删除会话
- 不删除 execution 与消息历史

这意味着：

- 历史列表中看不到该会话
- 若后续需要恢复能力，数据库中仍有基础记录

### 4. 消息历史接口保持不变

文件：

- `java-backend/src/main/java/robot/agent/controller/ChatController.java`
- `java-backend/src/main/java/robot/agent/service/ExecutionService.java`

`GET /api/sessions/{sessionId}/messages` 不需要为本次改造改变响应结构。  
历史消息的生成逻辑保持不变。

需要注意的只是：

- 会话是否进入历史列表，由列表接口决定
- 不是由消息接口单独决定

---

## 七、前端设计

### 1. 单一会话数据源

文件：

- `frontend/src/App.tsx`
- `frontend/src/components/SessionReplayPanel.tsx`

前端会话数据源统一放在 `App.tsx`。

`App.tsx` 负责：

- 拉取历史会话列表
- 创建会话
- 切换会话
- 删除会话
- 维护当前会话与历史集合

`SessionReplayPanel.tsx` 负责：

- 接收会话列表数据
- 展示历史会话
- 展示消息预览
- 触发选择与删除回调

这样可以避免历史面板再次自行发起“真相型请求”，降低状态分裂。

### 2. 新建会话行为

用户点击“新建会话”后：

1. 若当前会话已经发生过真实交互，则它应继续保留在历史列表中
2. 创建新的空会话并切换为当前会话
3. 新空会话不加入历史列表
4. 当前主聊天区正常显示该空会话

关键点：

- “当前会话”可以为空
- “历史列表”不能包含空会话

### 3. 删除会话行为

历史面板中每个历史会话项增加删除操作。

删除非当前会话：

1. 调用删除接口
2. 成功后从历史列表中移除
3. 当前聊天区不受影响

删除当前会话：

1. 调用删除接口
2. 断开当前 socket
3. 重置当前消息区与执行状态
4. 自动创建新的空会话并切换过去
5. 新空会话不进入历史列表

### 4. 历史面板展示规则

历史面板只展示后端返回的历史会话，不再在面板内自行决定“哪些 session 是历史”。

面板内仍可按需做以下轻量行为：

- 加载某个历史会话的消息内容
- 根据消息生成标题
- 展示时间、当前选中态

但不再做：

- 全量会话去重后推断历史
- 通过主动请求每个 session 的消息来决定该 session 是否应显示

### 5. 当前会话与历史会话关系

当前会话与历史会话不是互斥概念。

如果当前会话已经有真实交互，那么它在“数据语义”上已经属于历史会话，只是当前被激活使用。  
前端可继续在面板中展示它，并通过“当前”标识做区分。

## 八、数据流设计

### 场景 1：页面初次进入

1. 前端创建一个新的空会话作为当前会话
2. 前端请求历史会话列表
3. 后端返回：
   - 非 `DELETED`
   - 有真实用户交互
4. 前端显示：
   - 主聊天区：当前空会话
   - 历史面板：真实历史会话列表，不包含当前空会话

### 场景 2：当前空会话发送第一条消息

1. 用户发送消息
2. 后端创建 execution 并记录用户消息
3. 该会话自此满足“真实用户交互”条件
4. 前端刷新当前会话信息与历史列表后，该会话可作为历史会话存在

### 场景 3：已聊天的会话上点击新建会话

1. 当前会话已有真实交互
2. 用户点击新建会话
3. 前端创建一个新的空会话并切换
4. 旧会话仍保留在历史列表
5. 新会话不进入历史列表

### 场景 4：删除历史会话

1. 用户点击历史项删除
2. 后端将其状态改为 `DELETED`
3. 前端本地移除该历史项
4. 刷新页面后该会话也不会再次出现

### 场景 5：删除当前会话

1. 用户删除当前会话
2. 后端将其状态改为 `DELETED`
3. 前端清理 socket、消息、执行状态
4. 前端创建一个新的空会话并切换
5. 新空会话不进入历史列表

## 九、错误处理

### 1. 删除失败

前端提示删除失败，并保持原有列表不变。  
不允许本地先删除再无条件乐观覆盖，以免与后端状态不一致。

### 2. 新建会话成功但历史刷新失败

前端应保证当前会话创建与切换成功，即主聊天区可继续使用。  
历史列表可以保留旧数据，并记录错误日志；后续允许再次刷新。

### 3. 删除当前会话后新建空会话失败

前端应至少保证：

- 当前已删除会话不继续作为活跃会话使用
- 页面处于可恢复状态

推荐做法是显示错误并允许用户重试创建新会话。

## 十、测试设计

### 1. 后端测试

新增或补强以下测试：

1. `getSessionsByUserId()` 不返回 `DELETED` 会话
2. `getSessionsByUserId()` 不返回没有真实交互的空会话
3. `getSessionsByUserId()` 返回有真实交互的 `ACTIVE` / `CLOSED` 会话
4. `DELETE /api/sessions/{id}` 后会话状态变为 `DELETED`
5. `DELETED` 会话不再出现在列表中

### 2. 前端 E2E 测试

新增或修改以下场景：

1. 首次进入页面时，新建的空会话不显示在历史列表中
2. 当前会话发送消息后，再新建会话，旧会话应留在历史列表中
3. 连续新建多个但从未发送消息的空会话，历史列表不应累积这些空会话
4. 删除历史会话后，该项立即从历史列表消失
5. 删除当前会话后，页面自动切换到新的空会话，且历史列表不出现该空会话
6. 刷新页面后，历史列表结果与删除前后一致

### 3. 联调验证

联调至少覆盖：

1. 新建会话
2. 发第一条消息
3. 再新建会话
4. 切换历史会话
5. 删除历史会话
6. 删除当前会话
7. 刷新页面验证历史列表稳定

## 十二、不做的事情

本次不做以下扩展，避免范围失控：

1. 不实现会话恢复功能
2. 不实现回收站
3. 不做 execution 或 message 的物理删除
4. 不调整消息历史接口结构
5. 不做会话标题持久化，标题仍可由现有首条用户消息推导

---

## 十三、结论

本次设计的核心原则是：

1. 历史列表语义由后端定义，不由前端猜
2. 空会话不进历史
3. 删除是软删除，不是关闭
4. 前端用单一数据源管理会话状态

按此方案实施后，会话历史的创建、保留、删除、刷新行为将变得一致且可测试。
