# 能力中心（接口 / Skill / MCP）设计方案

**日期：** 2026-04-25

**目标：**
建设统一的“能力中心”配置与治理体系，按业务域集合组管理 `API / Skill / MCP` 三类能力，支持草稿/发布、认证授权、测试验证、流程接入与审计追踪，并保证流程只能调用已发布的稳定能力版本。

---

## 一、背景与问题

当前系统已经具备以下基础能力：

- 工作流具备草稿与发布版本机制
- 前端流程编排器已存在统一的 `tool` 节点
- Python 运行时已支持 `function / mcp / skill` 区分执行

但当前仍缺少统一的能力治理中心，主要问题如下：

1. 接口、Skill、MCP 没有统一的配置入口与管理模型
2. 缺少按业务域组织的集合组，流程侧难以稳定复用
3. 缺少独立的草稿/发布治理，无法保证流程只依赖稳定版本
4. 缺少统一测试验证能力，配置错误难以及时发现
5. 缺少集合组级别的快照机制，流程发布后无法锁定依赖
6. Skill 与 MCP 在流程中的调用边界、触发方式与测试方式尚未定义清楚

---

## 二、设计目标

本次设计需要满足以下目标：

1. 按业务域管理能力集合组，一个系统可配置多个集合组
2. 每个集合组下统一管理 `API / Skill / MCP` 三类能力
3. 集合组与能力项均支持新增、编辑、删除
4. 能力项支持草稿版本和发布版本
5. 集合组发布时生成发布快照，锁定一批已发布能力版本
6. 流程页面中调用能力时，先选集合组，再选组内能力
7. 流程运行时只能调用集合组发布快照中的已发布能力
8. 支持主流认证授权方式，并允许集合组默认配置与能力项覆盖
9. 配置后可测试，且测试结果可追溯
10. 为后续 Agent 节点绑定能力范围预留扩展能力

---

## 三、核心设计结论

### 1. 采用统一能力中心，而不是三套独立配置中心

本方案采用统一的“能力中心”模型，将 `API / Skill / MCP` 抽象为统一的“能力项”，由集合组承载治理、发布、测试和审计。

原因：

- 流程侧最终都表现为“调用某种能力”
- 三类能力都需要认证、版本、测试、发布治理
- 现有运行时已具备统一分发基础，重复建设三套体系成本过高

### 2. 集合组按业务域分组

集合组按业务域组织，例如：

- 用户域
- 订单域
- 支付域
- 内容域

环境信息、认证信息、目标地址等不作为第一层分组维度，而作为集合组配置或能力项配置的一部分管理。

### 3. 版本治理采用双层模型

- 能力项自身有草稿版与发布版
- 集合组发布时生成“发布快照”

流程不直接引用能力项草稿，也不直接引用集合组当前状态，而是引用集合组发布快照中的能力版本集合。

### 4. 流程统一使用“能力调用”节点

不再在流程设计器中拆出三个独立节点，而是在现有 `tool` 节点基础上升级为统一的“能力调用”节点，配置过程如下：

1. 选择集合组
2. 选择集合组发布快照
3. 选择能力类型
4. 选择具体能力
5. 配置入参映射、出参映射、失败策略

### 5. Skill 与 MCP 都有流程调用价值，但优先显式调用

- `MCP` 适合显式调用，因为本质是外部工具服务能力
- `Skill` 分两类：
  - 确定型 Skill：适合显式节点调用
  - Agent 型 Skill：更适合作为 Agent 节点可用能力范围

第一阶段统一采用显式调用，不依赖纯提示词隐式触发。

## 四、信息架构

### 1. 一级模块：能力中心

能力中心包含以下子模块：

- 集合组管理
- 能力项管理
- 认证与授权
- 测试验证
- 发布快照
- 调用审计

### 2. 一级对象：集合组

集合组是业务域级别的容器，负责：

- 聚合能力项
- 配置默认认证策略
- 配置默认环境策略
- 生成发布快照
- 作为流程选择入口

### 3. 二级对象：能力项

能力项统一抽象三类能力：

- `API`
- `Skill`
- `MCP`

每个能力项独立维护：

- 基础信息
- 类型专属配置
- 输入输出 Schema
- 认证绑定
- 环境绑定
- 草稿版 / 发布版
- 测试记录

### 4. 三级对象：集合组发布快照

集合组发布时生成快照，用于锁定一组已发布能力版本。快照是流程引用的稳定对象，不受后续草稿修改影响。

## 六、认证与授权设计

### 1. 支持的认证方式

第一阶段支持以下主流方式：

- OAuth 2.0
- JWT / Bearer Token
- API Key
- 账号 + 密码
- Basic Auth
- 自定义 Header
- 自定义 Query 参数
- 匿名访问

### 2. 认证配置层级

认证配置分两层：

- 集合组默认认证
- 能力项独立认证（可覆盖集合组默认值）

### 3. 安全要求

安全策略采用第一阶段推荐方案：

- 前端仅支持录入与掩码显示
- 敏感值不在页面明文回显
- 后端加密存储敏感字段
- 支持密钥轮换
- 支持测试凭据与生产凭据隔离

### 4. 认证失效影响

当认证配置变更时，需要标记依赖该认证的能力项为“待复测”状态，防止旧测试结论继续被误用。

---

## 七、版本治理设计

### 1. 能力项版本

能力项采用以下状态：

- `DRAFT`
- `PUBLISHED`
- `ARCHIVED`

能力项允许多个历史发布版本保留，用于回滚与审计。

### 2. 集合组快照

集合组发布不是简单状态切换，而是生成一份快照。快照内容包括：

- 集合组基础信息
- 该次发布纳入的能力项列表
- 每个能力项绑定的发布版本
- 认证与环境引用信息

### 3. 发布规则

集合组发布时必须满足：

1. 集合组内至少存在一个能力项
2. 被纳入快照的能力项必须都有发布版本
3. 关键能力项最近一次测试必须通过
4. 认证绑定必须有效

### 4. 流程引用规则

流程只能引用：

- 已发布的集合组快照
- 快照中存在的已发布能力版本

流程不能引用：

- 草稿能力项
- 未测试通过的关键能力项
- 未纳入快照的能力项

---

## 八、流程接入设计

### 1. 节点模型

流程设计器新增统一节点配置模型：`能力调用`

节点保存信息建议包含：

- `group_code`
- `group_snapshot_version`
- `capability_type`
- `capability_code`
- `capability_version`
- `input_mapping`
- `output_mapping`
- `failure_policy`

### 2. 用户操作路径

流程中配置节点时，用户操作路径为：

1. 选择集合组
2. 选择集合组快照
3. 选择能力类型
4. 选择具体能力
5. 配置输入参数映射
6. 配置输出参数映射
7. 配置异常处理策略

### 3. 运行时行为

运行时解析节点时：

1. 根据集合组快照获取能力版本定义
2. 装配认证信息
3. 解析输入参数
4. 分发到对应执行器（API / Skill / MCP）
5. 记录调用日志与结果

### 4. Agent 节点扩展

第二阶段允许 Agent 节点绑定集合组发布快照，表示 Agent 仅能在该集合组范围内进行工具选择。此时提示词只负责决策“是否调用”，可调用范围由集合组快照约束。

第一阶段不依赖此能力落地核心需求。

---

## 九、测试设计

测试设计遵循“按能力类型分层验证”的原则，不把测试简化为一次试跑。

### 1. API 测试

目标：

- 验证接口连通性
- 验证认证是否有效
- 验证请求参数是否正确
- 验证返回结果是否符合 Schema

建议页面动作：

- `测试连接`
- `发送测试请求`

返回信息：

- 请求参数
- 响应状态码
- 响应体
- 耗时
- 错误提示

### 2. MCP 测试

MCP 测试采用三段式：

#### （1）连接测试

验证：

- MCP Server 地址是否可达
- 协议是否正确
- 认证是否有效

#### （2）能力发现测试

验证：

- 是否成功读取 tools / resources / prompts
- 是否至少发现一个可用 tool
- tool 元数据是否可解析

#### （3）工具执行测试

验证：

- 选择某个 tool
- 输入测试参数
- 实际执行一次
- 校验返回结构与错误信息

页面按钮建议为：

- `测试连接`
- `发现能力`
- `执行测试`

返回信息包括：

- 连接状态
- Server 基本信息
- 发现到的工具数量
- 工具列表及 Schema
- 单次测试输入输出
- 耗时
- 错误原因

### 3. Skill 测试

Skill 测试采用三段式：

#### （1）配置校验

验证：

- Skill 元数据是否完整
- 输入输出 Schema 是否合法
- 依赖的认证、环境、子能力是否齐全

#### （2）样例执行

验证：

- 输入固定测试样例
- 执行 Skill
- 查看标准输出结果

#### （3）上下文模拟

验证：

- 模拟流程上下文变量
- 验证入参装配
- 验证执行逻辑
- 验证出参映射

若 Skill 属于 Agent 型，还应增加约束断言：

- 是否调用了未授权能力
- 是否命中预期输出结构
- 是否超时
- 是否进入异常恢复

页面按钮建议为：

- `校验配置`
- `运行测试`
- `上下文模拟`

返回信息包括：

- 输入
- 变量解析结果
- 执行日志
- 输出
- 断言结果
- 修复建议

### 4. 测试结果治理

测试记录需持久化保存，并至少包含：

- 测试类型
- 对应能力编码与版本
- 请求参数
- 响应结果
- 成功 / 失败
- 错误信息
- 耗时
- 测试时间
- 测试人

能力项状态中需要体现：

- 最近一次测试结果
- 是否因配置变更被标记为待复测

## 十、错误提示设计

### 1. 配置类错误

- `认证信息不完整，请补充 Client ID 和 Client Secret`
- `缺少必填参数：userId`
- `返回结果不符合输出 Schema：缺少 data.items`

### 2. 连接类错误

- `无法连接目标服务，请检查地址或网络策略`
- `认证失败，请检查 Token 是否有效`
- `连接超时，请检查服务可用性或超时配置`

### 3. MCP 特有错误

- `已连接 MCP Server，但未发现可用工具`
- `工具 schema 解析失败，请检查 MCP Server 返回`
- `工具执行失败，请检查参数或服务端日志`

### 4. Skill 特有错误

- `Skill 执行入口不可用`
- `上下文变量映射失败：orderId 未找到`
- `Skill 调用了未授权能力：payment.refund`

## 十二、与现有系统的衔接方案

### 1. 前端

建议复用现有流程设计器中的 `tool` 节点模型，升级为“能力调用”节点，避免新造一套节点类型体系。

同时新增“能力中心”页面，风格与现有模型配置页保持一致。

### 2. Java 后端

参考现有工作流版本体系，新增能力中心相关的：

- Model
- Repository
- Service
- Controller
- DTO

发布逻辑、草稿逻辑、回滚逻辑可复用当前工作流版本治理思路。

### 3. Python 运行时

保留现有 `tool` 节点执行分发机制，但将能力定义来源从节点直接配置扩展为“基于集合组快照解析能力定义”，统一完成：

- 认证装配
- 参数映射
- 风险确认
- 执行分发
- 审计记录

## 十三、范围划分

### 1. 第一阶段范围

本期纳入：

- 集合组管理
- 能力项管理
- API / Skill / MCP 基础配置
- 认证与授权配置
- API / Skill / MCP 测试能力
- 能力项发布
- 集合组发布快照
- 流程节点接入

### 2. 第二阶段范围

后续扩展：

- Agent 节点绑定集合组快照
- 更丰富的 Skill 评测断言
- MCP 资源和 Prompt 深度支持
- 密钥管理系统外接
- 审计报表与告警

### 3. 本期不做

本期不纳入以下内容：

1. 纯提示词驱动的隐式 Skill / MCP 调用治理
2. 外部 Vault / KMS 集成
3. 自动审批流程
4. 复杂多环境编排界面

---

## 十四、实施建议

建议实施顺序如下：

1. 先完成正式设计文档确认
2. 再拆分前端与后端实现计划
3. 前后端并行实现能力中心基础功能
4. 最后进行流程接入、联调与测试验证

---

## 十五、结论

本方案的核心原则是：

1. 用统一能力中心管理 `API / Skill / MCP`
2. 用业务域集合组组织能力
3. 用能力项发布版本 + 集合组发布快照保证流程稳定引用
4. 用显式“能力调用”节点保证流程可控、可测、可审计
5. 用分层测试机制保证 API、Skill、MCP 的配置可验证

按此方案实施后，系统将具备一套统一、稳定、可扩展的能力配置与调用治理体系，并为后续 Agent 化扩展保留清晰边界。
