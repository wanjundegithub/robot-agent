# 意图识别流程设计方案

## 1. 背景

当前系统采用 multi-agent 工作流设计，协调者节点负责根据用户输入识别意图，并将请求路由到对应流程或子流程。现阶段需要设计一套低延时、高准确率的意图识别流程，同时尽量减少大模型调用次数。

本方案选择串行三段式识别路径：先规则匹配，再 RAG 召回，最后由大模型兜底。系统只在规则和 RAG 无法可靠判断时调用大模型，避免每次用户输入都进入大模型判断。

## 2. 设计目标

1. 优先减少大模型调用，降低成本和响应延时。
2. 对高确定性输入快速命中，直接进入对应流程或子流程。
3. 对中低置信输入保持谨慎，避免误进入错误流程。
4. 支持一次用户输入识别出多个候选意图，并按置信度顺序处理。
5. 当无法识别意图时，向用户再次提问，获取更多信息。

## 3. 非目标

1. 暂不引入规则强弱分层。
2. 暂不引入复杂仲裁器或并行识别。
3. 暂不建设人工标注闭环。
4. 暂不设计高风险意图的二次确认机制。
5. 暂不实现具体代码和数据表结构。

## 4. 总体流程

用户输入进入意图识别后，按以下顺序处理：

1. 正则匹配用户输入。
2. 如果正则匹配成功，直接认定命中对应意图，并进入对应流程或子流程。
3. 如果正则未匹配，进入 RAG 意图搜索。
4. 如果 RAG 召回的最高分意图达到设定阈值，认定命中该意图。
5. 如果 RAG 最高分未达到阈值，进入大模型兜底判断。
6. 如果大模型判断命中，则进入对应流程或子流程。
7. 如果大模型也判断未命中，则认为当前输入无匹配意图，向用户再次提问。

流程表达如下：

```text
用户输入
  ↓
正则匹配
  ├─ 命中 → 进入对应流程/子流程
  ↓ 未命中
RAG 意图搜索
  ├─ 最高分 ≥ 阈值 → 进入对应流程/子流程
  ↓ 低于阈值
LLM 兜底判断
  ├─ 命中 → 进入对应流程/子流程
  ↓ 未命中
向用户追问
```

## 5. 正则匹配阶段

正则匹配用于处理确定性强、表达稳定、业务边界清晰的意图。

适合配置正则的场景：

1. 用户输入包含明确命令词，例如“查订单”“取消订单”“预约维修”。
2. 用户输入包含稳定业务编号或格式，例如订单号、工单号、航班号。
3. 某些入口词与具体流程高度绑定，误判风险较低。

正则匹配结果应至少包含：

1. `intent_code`：命中的意图编码。
2. `target_type`：目标类型，取值为 `workflow` 或 `subflow`。
3. `target_code`：目标流程或子流程编码。
4. `confidence`：规则命中置信度，正则命中时可固定为高置信。
5. `matched_pattern`：命中的正则规则标识。

正则命中后不再调用 RAG 和大模型，直接进入目标流程或子流程。

## 6. RAG 意图搜索阶段

当正则未命中时，系统进入 RAG 意图搜索。RAG 的知识来源是已发布或可运行的意图配置，内容包括意图名称、意图描述、典型用户说法、关联流程、关联子流程等。

RAG 召回后按相似度排序，取 Top-K 候选意图。系统比较最高分候选与设定阈值：

1. 如果最高分大于或等于阈值，认定该候选意图命中。
2. 如果最高分低于阈值，认为 RAG 无法可靠判断，进入大模型兜底。

RAG 匹配结果应至少包含：

1. `intent_code`：候选意图编码。
2. `target_type`：目标类型，取值为 `workflow` 或 `subflow`。
3. `target_code`：目标流程或子流程编码。
4. `confidence`：RAG 相似度归一化后的置信度。
5. `matched_evidence`：召回依据，例如命中的示例话术或意图描述片段。

## 7. 大模型兜底阶段

大模型只作为第三步兜底，不作为常规识别入口。只有在正则未命中且 RAG 最高分低于阈值时，才调用大模型。

大模型输入应尽量小，只包含：

1. 用户原始输入。
2. 归一化后的用户输入。
3. RAG Top-K 候选意图。
4. 每个候选意图的名称、描述、目标流程或子流程。
5. 当前会话中必要的上下文摘要。

大模型不应接收全量意图库，避免成本和延时不可控。

大模型输出必须使用结构化格式：

```json
{
  "matched": true,
  "intent_code": "intent_order_query",
  "target_type": "workflow",
  "target_code": "order_query",
  "confidence": 0.76,
  "reason": "用户表达了查询订单状态的需求",
  "need_clarification": false,
  "clarification_question": null
}
```

如果大模型无法确认匹配，应输出：

```json
{
  "matched": false,
  "intent_code": null,
  "target_type": null,
  "target_code": null,
  "confidence": 0.0,
  "reason": "用户输入缺少明确业务目标",
  "need_clarification": true,
  "clarification_question": "请问你想办理哪类业务？"
}
```

当 `matched=false` 时，系统不进入任何流程，而是向用户发送 `clarification_question`。如果大模型没有给出追问内容，系统使用默认追问文案。

## 8. 多意图队列

一次用户输入可能同时包含多个意图。例如用户说“帮我查一下订单，再取消明天的预约”。系统应支持识别多个候选意图，并按置信度排序执行。

处理规则如下：

1. 所有阶段都可以返回一个或多个候选意图。
2. 系统按置信度从高到低排序候选意图。
3. 置信度最高的意图作为主意图立即执行。
4. 其余候选意图进入当前会话的候选意图队列。
5. 主意图执行完成后，从队列中取出下一个候选意图。
6. 执行候选意图前，必须向用户确认是否继续。
7. 用户确认后，执行该候选意图。
8. 用户拒绝后，丢弃该候选意图并继续检查队列。
9. 队列为空后，本轮多意图处理结束。

候选队列元素建议包含：

```json
{
  "intent_code": "intent_cancel_booking",
  "target_type": "workflow",
  "target_code": "booking_cancel",
  "confidence": 0.71,
  "source": "rag",
  "evidence": "用户提到取消明天的预约",
  "created_at": "2026-05-07T21:00:00+08:00"
}
```

确认文案示例：

```text
刚才还识别到你可能想要“取消预约”，是否继续办理？
```

## 9. LLM 调用控制

为了减少大模型调用，本方案采用以下控制规则：

1. 正则命中后直接返回，不调用 RAG 和大模型。
2. RAG 达到阈值后直接返回，不调用大模型。
3. 只有正则未命中且 RAG 未达到阈值时，才调用大模型。
4. 大模型只接收 RAG Top-K 候选和必要上下文，不接收全量意图库。
5. 对相同用户输入和相同上下文摘要，可以使用短 TTL 缓存复用大模型判断结果。
6. 大模型返回结果必须经过结构化解析，解析失败时按无匹配处理并向用户追问。

推荐的缓存 Key 组成：

```text
hash(normalized_user_input + session_context_summary + rag_candidate_codes)
```

缓存 TTL 可设置为 5 到 30 分钟，具体由业务对实时性的要求决定。

## 10. 置信度与阈值

本方案至少需要配置以下阈值：

1. `rag_accept_threshold`：RAG 自动命中阈值。
2. `llm_accept_threshold`：大模型兜底命中阈值。
3. `candidate_queue_threshold`：进入候选意图队列的最低置信度。
4. `rag_top_k`：传给大模型的 RAG 候选数量。

建议初始值：

```yaml
rag_accept_threshold: 0.80
llm_accept_threshold: 0.70
candidate_queue_threshold: 0.60
rag_top_k: 5
```

这些阈值应作为配置项管理，便于根据线上效果调整。

## 11. 无匹配追问策略

当三个阶段都无法确认用户意图时，系统应再次向用户提问。

追问策略：

1. 如果大模型返回了 `clarification_question`，优先使用该问题。
2. 如果没有可用问题，使用系统默认文案。
3. 追问后用户的新输入重新进入完整识别流程。
4. 追问次数可以设置上限，超过上限后转人工或给出可选业务列表。

默认追问文案：

```text
我还不确定你想办理什么业务，可以再具体说明一下吗？
```

## 12. 与工作流运行的关系

意图识别只负责决定进入哪个流程或子流程，不负责执行具体节点。

当识别命中后，系统输出统一路由结果：

```json
{
  "matched": true,
  "intent_code": "intent_order_query",
  "target_type": "workflow",
  "target_code": "order_query",
  "confidence": 0.92,
  "source": "regex",
  "candidate_queue": []
}
```

工作流运行器根据 `target_type` 和 `target_code` 启动对应流程或子流程。进入流程后，槽位提取、表单追问、节点执行、变量读写仍由现有工作流机制负责。

## 13. 运行指标

为验证方案效果，应记录以下指标：

1. 正则命中率。
2. RAG 命中率。
3. 大模型兜底调用率。
4. 无匹配率。
5. 用户确认候选意图的通过率。
6. 用户拒绝候选意图的比例。
7. 意图识别总耗时。
8. 各阶段耗时。

重点观察大模型兜底调用率。如果调用率偏高，应优先优化正则配置和 RAG 意图语料。

## 14. 边界场景

1. 正则命中多个意图：按规则配置的优先级或置信度排序，最高者执行，其余进入候选队列。
2. RAG 召回多个高分意图：最高者执行，其余达到队列阈值的候选进入队列。
3. 大模型返回多个候选：最高置信度候选执行，其余达到队列阈值的候选进入队列。
4. 候选意图目标已下线：丢弃该候选，并记录异常日志。
5. 用户在确认候选意图时提出新需求：放弃当前确认动作，将新输入重新进入意图识别流程。

## 15. 验收标准

1. 正则命中时不会调用 RAG 和大模型。
2. RAG 达到阈值时不会调用大模型。
3. 只有前两步未命中时才调用大模型。
4. 无匹配时系统会向用户追问。
5. 多个候选意图会按置信度排序。
6. 主意图执行完成后，候选队列会逐个向用户确认。
7. 大模型输出必须是结构化结果，无法解析时不会误进入流程。
8. 识别结果能明确给出目标流程或子流程。
