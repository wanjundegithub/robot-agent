# 代码 Bug 定位与修复

使用此 Skill 时，必须以“先定位和解释，再征求认可，最后修复和测试”为主线。除非用户已经明确要求立即修改，否则不要在完成原因分析和方案确认前改代码。

## 工作流

1. 收集输入
   - 读取用户提供的文字报错、日志、堆栈、测试失败输出、截图或界面现象。
   - 如果用户提供图片，先提取图片中的关键错误文本、文件名、行号、状态码、组件名、按钮文字、页面状态等可定位信息。
   - 如果信息不足以判断问题范围，先提出最少数量的澄清问题；如果可以通过本地代码、测试或日志继续定位，则优先自行检查。

2. 建立可验证假设
   - 根据报错内容识别错误类型：语法错误、类型错误、依赖缺失、接口契约不一致、状态管理错误、并发/异步问题、编码问题、路径问题、环境配置问题、权限问题、数据边界问题或 UI 渲染问题。
   - 使用 `rg`、测试、类型检查、日志和代码调用链定位相关文件与函数。
   - 不要只根据报错表面猜测；至少找到一个能解释现象的代码位置或配置位置。

3. 说明原因和影响范围
   - 向用户说明：
     - Bug 出现在哪里。
     - 触发条件是什么。
     - 根因是什么。
     - 为什么当前代码会导致该报错或异常行为。
     - 预计修复会影响哪些模块、接口、数据结构、配置或用户路径。
   - 如果修复可能影响其他功能点、公共 API、数据库结构、配置格式、测试基线或用户可见行为，必须暂停并向用户确认后再修改。

4. 给出修复方案
   - 优先选择最小范围、低风险、符合现有代码风格的方案。
   - 明确说明不会改变的边界，例如不改公共接口、不改无关模块、不扩大依赖、不重构无关代码。
   - 如果存在多个方案，简要比较风险和收益，并给出推荐方案。
   - 在用户认可方案后再实施修复；如果用户已经明确授权“直接修复”或“帮我改好”，可以在说明方案后继续执行，但仍要遵守影响范围边界。

5. 实施修复
   - 修改与 Bug 直接相关的最小文件集合。
   - 不要顺手重构无关代码。
   - 不要回滚用户已有改动。
   - 保持文件原始编码，使用 UTF-8，不破坏中文、日文、emoji 等 Unicode 字符。
   - 修复时优先补充或调整能复现该 Bug 的测试；如果测试成本过高，至少说明为什么没有新增测试。

6. 验证修复
   - 运行最贴近 Bug 的测试、类型检查、lint、构建或手动复现步骤。
   - 如果用户提供的是 UI/截图类问题，尽量用浏览器、截图或可观察输出验证修复后的界面状态。
   - 如果验证失败，继续定位失败原因，不要声称已修复。
   - 如果无法运行测试或验证命令受限，明确说明限制、已完成的检查和剩余风险。

## 输出要求

在修复前，输出应包含：

- `问题定位`：相关文件、函数、调用链或配置位置。
- `原因分析`：报错或异常行为的直接原因和根因。
- `修复方案`：准备怎么改、为什么这样改、影响边界是什么。
- `需要确认`：当修复可能影响其他功能点时，明确请求用户确认。

在修复后，输出应包含：

- `已修改`：实际改动的文件和行为变化。
- `验证`：运行过的测试/检查命令及结果。
- `边界说明`：确认未触及的功能范围，或说明仍存在的风险。

## 边界规则

- 如果没有足够证据定位问题，不要直接改代码。
- 如果修复会改变用户未提到的功能行为，必须先确认。
- 如果修复需要升级依赖、改数据库、改 API 契约、改鉴权/权限、改部署配置或影响兼容性，必须先确认。
- 如果用户只要求分析，不要修改代码。
- 如果用户要求修复但没有明确授权高风险改动，只能做最小安全修复。
- 如果发现多个无关 Bug，只修复当前用户请求覆盖的问题；其他问题作为后续建议提出。

## 常用定位方法

- 用报错中的文件名、函数名、类名、错误码、接口路径、测试名作为 `rg` 搜索关键词。
- 从最靠近失败点的代码开始读，再向调用方和数据来源回溯。
- 对空值、类型不匹配、数组越界、异步竞态、路径大小写、编码、时区和环境变量进行重点检查。
- 对截图类问题，优先确认实际 UI 状态、控制台错误、网络请求失败、样式覆盖和响应式布局边界。
- 对测试失败，先复现单个失败测试，再扩大到相关测试集。
